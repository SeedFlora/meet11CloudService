# Supabase, keamanan data, dan deployment

Supabase menyediakan PostgreSQL, autentikasi, penyimpanan objek, dan API. Saat aplikasi Next.js memakai Supabase dari browser, publishable key mengidentifikasi project tetapi bukan otorisasi penuh. Identitas user berasal dari sesi Auth. Database menerapkan Row Level Security (RLS) untuk menentukan baris mana yang terlihat atau dapat diubah. Service role atau secret key melewati RLS dan karena itu hanya boleh berada di server terpercaya; jangan membundelnya dengan nama environment variable berawalan `NEXT_PUBLIC_`.

Contoh tabel `notes` memiliki kolom `user_id` yang merujuk `auth.users(id)`. Policy SELECT mengizinkan pengguna terautentikasi membaca baris ketika `user_id = auth.uid()`. Policy INSERT memakai `WITH CHECK` agar pengguna tidak dapat menulis catatan dengan pemilik orang lain. UPDATE perlu syarat `USING` untuk memilih baris lama serta `WITH CHECK` untuk memastikan pemilik baris baru tetap sah. DELETE hanya berlaku pada baris pemilik. Ketika tidak ada sesi, `auth.uid()` bernilai NULL; policy yang menuntut identitas akan menolak akses.

Grants dan policy adalah dua pemeriksaan terpisah. Grant menentukan operasi SQL apa yang tersedia untuk role; policy menentukan baris mana yang lolos. Tabel yang hanya punya policy tetapi memberikan hak terlalu luas kepada role anonim masih membuka jalur yang tidak diinginkan ketika policy berubah. Sebaliknya, policy yang benar tanpa grant yang diperlukan akan menghasilkan error izin. Lab 07 mencabut akses `anon` ke tabel notes dan memberi role `authenticated` operasi terbatas, lalu menyalakan RLS.

Jangan menganggap setiap bucket Storage otomatis aman. Bucket private memerlukan policy objek untuk operasi yang ingin diizinkan. Tautan file publik harus dipakai hanya untuk materi yang memang boleh dipublikasikan. Data latihan sebaiknya sintetis: tidak ada nomor identitas, password, token API, atau dokumen pribadi. Untuk capstone, tentukan klasifikasi data sebelum merancang public URL dan log aplikasi.

Next.js App Router dapat menjalankan Server Component untuk mengambil data di server dan Client Component untuk interaksi browser. Route Handler pada `app/api/.../route.ts` menanggapi HTTP GET/POST dan dapat bertindak sebagai backend kecil. Variabel tanpa awalan `NEXT_PUBLIC_` tetap di server. Variabel dengan awalan tersebut dapat masuk ke bundle browser, sehingga hanya konfigurasi yang aman untuk publik boleh dipakai. Setelah aplikasi dihubungkan ke GitHub, Vercel dapat membuat preview deployment dari branch dan deployment produksi dari branch utama. Environment variables diatur pada platform; jangan commit `.env.local`.

Deployment yang dapat diulang memerlukan riwayat Git yang jelas, instruksi setup, migrasi schema, dan pemeriksaan build. Reproduksi lokal penting ketika layanan luar gagal atau syarat plan berubah. Public URL adalah bukti deployment, tetapi belum membuktikan keamanan atau keandalan. Uji dua akun terpisah untuk memastikan RLS, uji URL health, dan periksa log server untuk kegagalan. Health endpoint yang hanya mengembalikan `ok` adalah liveness; readiness harus memeriksa dependency yang benar-benar dibutuhkan fitur utama.

Observability memakai metrics, logs, dan traces. Metrics membantu melihat tingkat error dan latensi sepanjang waktu. Log terstruktur membantu menemukan request dengan ID dan status tanpa memuat secret. Trace menunjukkan perjalanan satu request antar service. Uptime check sintetis mencatat apakah endpoint merespons, tetapi tidak mengukur semua pengalaman pengguna. SLI adalah ukuran layanan, SLO adalah targetnya, dan error budget adalah porsi kegagalan yang dapat diterima selama periode tertentu. Untuk web performance, metrik Core Web Vitals kini adalah LCP, INP, dan CLS; FID adalah metrik historis yang digantikan INP.
