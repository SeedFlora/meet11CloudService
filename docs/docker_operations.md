# Container, Dockerfile, dan Compose

Image adalah template yang berisi filesystem dan metadata untuk menjalankan proses. Container adalah instans proses terisolasi dari image tersebut. Menghentikan container tidak otomatis menghapus image; menghapus container tidak otomatis menghapus volume. VM biasanya membawa guest operating system sendiri, sedangkan container berbagi kernel host melalui mekanisme isolasi. Di Linux, namespaces memisahkan pandangan proses terhadap jaringan, mount, dan identitas; cgroups membatasi sumber daya seperti CPU dan memori.

Dockerfile menjelaskan cara membangun image. WORKDIR menetapkan direktori kerja, COPY menyalin file dari build context, RUN menjalankan perintah saat build, dan CMD menetapkan proses default ketika container dijalankan. EXPOSE adalah dokumentasi port pada image, bukan perintah membuka port pada host. Port host baru dipetakan dengan opsi `-p` atau bagian `ports` di Compose. ENV dapat dipakai untuk konfigurasi non-rahasia, tetapi secret tidak boleh ditanam dalam image karena layer dan registry dapat membocorkannya.

Multi-stage build memisahkan tahap builder dari tahap runtime. Builder dapat berisi compiler atau alat pemasangan dependency, sedangkan runtime hanya membawa yang diperlukan untuk melayani request. Pengurangan ukuran image dapat mempercepat pengiriman dan memperkecil permukaan serangan. `.dockerignore` mengecualikan virtual environment, cache, file `.env`, dan file yang tidak perlu dari build context. Tag seperti `cloud-notes-api:lab05` membantu mendokumentasikan versi, tetapi untuk produksi sebaiknya gunakan versi yang jelas dan proses rilis yang dapat ditelusuri.

Docker Compose mendefinisikan beberapa service dalam satu YAML. Dalam proyek kelas, service `api` berbicara ke `db` melalui hostname `db` dan ke Redis melalui hostname `cache`. `localhost` di dalam container API menunjuk container API itu sendiri, bukan database atau laptop. Compose menyediakan network proyek secara otomatis. Dari laptop, akses API terjadi melalui port yang dipetakan ke `127.0.0.1:8000`. Membatasi binding ke loopback membantu mencegah service latihan terlihat oleh perangkat lain di jaringan.

`depends_on` dengan kondisi `service_healthy` membuat API menunggu healthcheck DB dan cache lulus sebelum dimulai. Urutan start biasa tidak menjamin database siap menerima query. Healthcheck harus memeriksa kemampuan dasar service, misalnya `pg_isready` untuk PostgreSQL dan `redis-cli ping` untuk Redis. Aplikasi tetap perlu menangani kegagalan setelah startup, karena dependency dapat berhenti kapan saja.

Named volume menyimpan data di luar filesystem sementara container. Ketika API atau DB container dibuat ulang, volume dapat dipasang kembali dan catatan tetap ada. `docker compose down` menghentikan dan menghapus container/network proyek, tetapi mempertahankan volume. `docker compose down -v` juga menghapus volume sehingga data latihan hilang. Perintah pembersihan ini harus digunakan dengan sadar setelah backup atau ketika data tidak dibutuhkan.

Redis dapat menyimpan daftar catatan sementara untuk mengurangi query PostgreSQL. Pada pola cache-aside, aplikasi membaca cache lebih dulu, lalu DB bila cache kosong. Setelah menulis atau menghapus catatan, aplikasi menghapus entri cache terkait. TTL memberi batas umur data cache. Cache bukan sumber kebenaran; bila Redis gagal, aplikasi sebaiknya masih bisa membaca data dari PostgreSQL. Header `X-Cache: HIT` dan `X-Cache: MISS` pada lab membantu mengamati perilaku tersebut.

Profile Compose mengaktifkan service tambahan seperti Adminer saat debugging. Service inti sebaiknya aktif tanpa profile sehingga perintah `docker compose up` menghasilkan aplikasi yang dapat digunakan. Secret berbasis file memberi DB dan API password melalui `/run/secrets`; source asli diabaikan Git. File contoh boleh dikomit, sedangkan file dengan nilai nyata tidak boleh. Ini praktik dasar sebelum memakai pengelola secret dari platform produksi.
